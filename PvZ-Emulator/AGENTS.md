# PvZ-Emulator 项目约束

## 说明

bugfix 分支中过度新增的高层接口已经完成回退。当前仓库只保留 Legacy PE
C++ 公共 API、真实 bug 修复、少量必要的修改器/观测原子，以及原模拟器内部
本来就有但此前没有暴露的底层操作。PE 仓库内不再保存 RSVZ 专用的 C/Rust
facade、snapshot、测算协议或高层 helper；Rust bridge、确定性 setup 和组合语义
位于相邻 `RustVsZombies/` 的 PE adapter、backend 与 core。不要从历史提交或
bug 台账恢复这些已裁撤 facade。

新增 PE 接口时仍应让抽象层级接近 PvZ 1.0.0.1051 的原子接口；更加抽象的
批量或策略语义放到 RSVZ。跨 FFI 已配置 LTO，因此不能为了减少调用次数而把
大对象复制、snapshot 或高层批量语义重新下沉到 PE。

## 项目定位

本项目是一个 PvZ 生存无尽 / 阵型测算用的纯游戏逻辑模拟器，没有图形化界面。**不是**完整复刻原版 PvZ 全部模式、UI、商店进度和一次性救场资源的全功能模拟器。

判断行为差异时，优先区分：

- 无尽核心战斗机制差异：默认可疑，应按反汇编、objdump 或测试验证。
- 无尽测算策略下刻意保留的非 bug 差异。
- PE 暂不覆盖的非主路径、表现层或低优先级边界。
- 历史已修 bug 或已知问题记录，应参考对应文档与 commit。

另外，`../PlantsVsZombies-decompilation` 反编译源码不是绝对权威；已确认的反编译源码与原版 1.0.0.1051 二进制不一致项记录在 `反汇编项目的错误.md`。遇到该文件列出的函数时，应以 Ghidra / `objdump` 复核结果为准。


## 按任务读取资料

| 本次任务 | 阅读入口 |
| --- | --- |
| 判断游戏行为差异、修改机制或设计 parity 测试 | [机制差异](机制差异.md)中涉及的机制；区分设计取舍、非目标范围与真实 bug |
| 修复核心战斗机制、核验地址或分支 | [二进制核验](二进制核验.md)，并检索相关错误台账 |
| 构建、工具配置或纯文档修改 | 受影响配置和文档；仅在需要二进制工具时读取其操作说明 |

PE 核心 subsystem 与单个 world 保持单线程，不新增锁、原子量、async 或
worker。legacy `world::update_all()` 仅批量推进互不相同的 world；RSVZ
每个 worker 独占 world，不调用该 helper。对象池元素保持纯数据；引入自定义
构造、析构、赋值或资源所有权前，须重审对象池生命周期语义。

## 原版对齐原则

以下无尽核心战斗机制应尽量对齐 PvZ 1.0.0.1051 原版：

- 僵尸运动、攻击、受击、冻结、减速、黄油
- 植物攻击、装填、生效时机、特殊行为
- 出怪（spawn）：波次、刷新、权重、同屏限制、红眼概率
- 子弹碰撞、溅射、特殊防具交互（火抗、门板、梯子）
- 阵型相关种植判定（升级植物、南瓜头规则、加农炮双格）
- 蹦极僵尸目标选择与优先级
- 投篮车/巨人/伴舞等特殊僵尸行为
- 冰道生成、持续与辣椒清除

## 二进制证据

无尽核心机制以 1.0.0.1051 原版二进制或真实运行验证为最终依据；反编译源码
用于定位和理解候选逻辑。Ghidra 不可用时用 `objdump` 继续，不能以源码猜测
替代二进制证据。具体核验流程和本机工具入口见 [二进制核验](二进制核验.md)。

## 文档规则

| 文件 | 用途 |
| --- | --- |
| `已经修改的bug合集.md` | 只记录真正修复的代码 bug；已提交项注明提交 hash，未提交项标注待提交；最新代码已提交但等待下一轮补录 hash 时标注待补提交号 |
| `pe模拟器问题合集.md` | 只记录尚未修复或待设计确认的 PE 行为差异；修复并写入 `已经修改的bug合集.md` 后应从本文件移除 |
| `反汇编项目的错误.md` | 记录反编译源码与原版二进制不一致的已确认项目，审查这些函数时以二进制为准 |
| [机制差异.md](机制差异.md) | 已确认的设计取舍、非目标范围及证据边界 |
| [二进制核验.md](二进制核验.md) | 按需读取的核验流程和本机工具说明 |
| `AGENTS.md` | 项目硬约束与文档路由（本文件） |

提交号采用滞后一轮补录：完成实质代码提交后，最新修复记录可以暂写“待补提交号”；
下次发生实质代码修改时，再把上一轮记录更新为实际 hash，并随本次代码或相关
文档一起提交。不得仅为补 hash、迁移台账或更新验证文字创建独立文档提交；如果
尚无下一次实质修改，允许最新一项继续保持“待补提交号”。

**刻意差异应明确标注为"非 bug / 设计取舍 / 无尽测算策略"，不应写入"已修改的 bug 合集"。**
