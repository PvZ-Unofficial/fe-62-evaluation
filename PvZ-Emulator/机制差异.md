# 刻意保留 / 暂不覆盖的非目标差异

以下行为看起来和原版反编译不一致，但属于无尽测算场景的刻意取舍、当前非目标范围或低优先级边界。除非用户明确要求，或有证据表明它影响无尽测算，**不应视为必须修复的 bug**。

### 1. 默认无小推车

PE 默认不模拟小推车（Lawnmower/PoolCleaner）。僵尸进家直接判负。

原因：无尽模式中小推车是一次性资源。如果阵型需要依赖小推车才能过关，则不应视为可无尽。默认无小推车可以更早暴露阵型失败，避免一次性救场资源掩盖问题。

测试验证：`petest` 中 `test_scene_geometry_and_main_counter` 检查。

除非用户明确要求完整原版小推车模拟，否则不要添加 `lawnmower` 对象/系统，也不要把"没有小推车"列为待修 bug。

### 2. 默认视为商店/进度能力已解锁

PE 面向无尽测算时，默认假定与无尽阵型相关的进度能力已经解锁，包括但不限于：

- 南瓜修补术（可在南瓜上直接种新南瓜）
- 全部植物可用（无需模拟购买解锁流程）
- 全部 10 个卡槽可用

PE 没有商店系统、没有购买记录、没有冒险模式进度存档。不要把"没有模拟商店/进度"当作 bug。

### 3. 初始阳光为 9990

`scene::sun.sun` 默认值为 `9990`，对应无尽模式初始阳光。原版冒险模式初始阳光为 50~150 不等。PE 选择无尽基线是刻意的，不应改为其他默认值。

连续全难度资源评估可以显式设置每个世界的 `scene::sun.limit`。默认及世界 reset 后仍为 9990；更高的值属于测算配置，不是原版机制修复。植物产阳光和自然掉落共用这个上限，种植仍正常扣费；不同世界之间互不影响。

### 4. 覆盖常规六场景和蘑菇园无尽

PE 只支持：

- `day`（白天）
- `night`（黑夜）
- `pool`（泳池）
- `fog`（迷雾）
- `roof`（屋顶）
- `moon_night`（月夜）
- `mushroom_garden`（蘑菇园无尽：夜间五行陆地，无墓碑，允许冰车）

不支持：小游戏、花瓶破碎者、我是僵尸、坚果保龄球、僵尸水族馆等非无尽主路径模式。不要把"缺少某小游戏模式"列为需要修复的 bug。

### 5. 默认构造不等于完全初始化

`world(scene_type)` 构造函数只初始化成员，**不调用** `spawn.reset()`。`spawn.reset()` 在 `world::reset()` 或 `world::reset(scene_type)` 中才会被调用。

这意味着：

```cpp
world w(scene_type::pool);
// w 的 spawn_list / spawn_flags 尚未生成
// 需要先调用 w.reset() 才会生成完整的出怪模型
```

这是 API 设计上"构造和解初始化"的刻意分离。`spawn::spawn()` 构造函数已为数据成员设好基础默认值，但波次生成是重量级 RNG 操作，由使用者显式触发。

测试验证：`peparitytest` 中 `test_deferred_copy_and_public_input_safety` 检查。

### 6. 纯游戏逻辑，无表现层

PE 不模拟以下原版系统：

- 粒子效果、音效、背景音乐
- 光标、UI 按钮、卡片选择界面
- 商店界面、对话、字幕
- 过场动画（cutscene）
- 墓碑/冰道的视觉渲染（但有逻辑数据 `ice_path`）

这些不是无尽核心战斗机制，添加它们对测算收益极低，不要默认添加。

### 7. 无金币/物品/花园系统

PE 不包含：

- 金币、银币、钻石
- 巧克力、礼物盒
- 禅境花园（Zen Garden）
- 图鉴（Almanac）
- 成就系统

不要把"缺少金币掉落"列为 bug。

### 8. `obj_list` 使用 `T{}` 赋值而非 `memset`

`obj_list::alloc()` 在分配槽位时执行 `a[i].t = T{};`，而不是原版 DataArray 的 `memset + placement new`。

这个差异意味着：**不要往 `obj_list` 里放带自定义构造、析构、赋值语义或拥有资源的非纯数据类型**，除非后续同时重审对象池生命周期语义。当前所有模板实例化类型（plant/zombie/projectile/griditem）都是纯 C 风格数据，不受此简化影响。

### 9. 单线程，无并发

原版游戏是单线程程序。除下述 legacy 批量包装器外，PE 核心 subsystem 不使用 `Mutex`、`Atomic`、`async`、worker thread、lock-based command system 等并发原语；单个 world 的所有游戏状态访问都是单线程的。

不要为了"Rust 最佳实践"或"现代 C++ 并发"引入线程/锁。需要内部可变状态时使用单线程设施。

历史例外：legacy `world::update_all()` 会在一次批处理中用 worker 推进多个**互不相同**的 world；它会拒绝空指针和重复 world 指针，不能让同一个 world 被并发访问。RSVZ runner 不调用该 helper，而是由每个 Rust worker 独占一个 world。不要把这个兼容入口扩散到核心 subsystem，也不要据此宣称单个 world 线程安全。

### 10. 裂荚射手 `mLoopCount` 边界暂不模拟

原版裂荚射手的前后头射击状态依赖 `Reanimation::mLoopType` 和 `mLoopCount`。当前 PE 不模拟图形化 reanimation，因此只用 `split_pea_attack_flags.front/back` 模拟会影响战斗的 shooting-hold 状态残留。

当前实现应保持对齐以下常规无尽测算中的核心裂荚 bug 行为：

- `mLaunchCounter == 25` 的首轮前后头攻击中，前后都有僵尸时，前后各两发。
- 首轮前方有目标、`mLaunchCounter <= 0` 第二轮后头攻击前，前方目标已消失时，前方仍补第二发。
- 首轮前方无目标、第二轮后头攻击前，才出现前方目标时，不误发前方第二发。

但 PE 暂不模拟原版 `mLoopCount > 0` 才清除头部 hold 状态的极端边界。这可能只影响"新种下裂荚 + 很早开火 + 目标方向随后变化"的早期状态残留。在没有证据表明该边界影响无尽测算前，不要为了它引入完整 reanimation 系统；如需修复，应做最小逻辑状态模拟，而不是添加图形/表现层。

### 11. 默认 1000 flags 后高周目无尽出怪

PE 默认 `scene::spawn_data::total_flags = 1000`，用于模拟高周目无尽测算，而不是从 0 flags 或低周目生存阶段开始。

因此，下列行为在当前默认语义下属于高周目无尽策略，**不要直接列为 bug**：

- 每波固定生成/填满 50 个出怪槽。原版自然出怪受点数和 `MAX_ZOMBIES_IN_WAVE` 限制；高 flags 后点数足够，125 关以后自然会饱和到每波 50 只。
- 出怪类型复杂度一开始就是满额。原版 `InitZombieWavesSurvival` 的容量是 `min(mSurvivalStage + 1, 9)`；高周目后容量已经达到 9。
- 默认允许雪人。PE 假定无尽相关账号进度已经解锁；原版 `Challenge::InitZombieWaves` 在 `CanSpawnYetis()` 成立时会把雪人加入允许表。

仍应视为 bug 的是：在高周目默认语义下，本应可自然出怪的红眼巨人因为候选遍历或枚举洞等实现问题无法进入实际波表。若未来明确支持低 flags / 未解锁账号 / 低周目自然出怪，应新增显式配置并按原版点数、容量和进度规则生成，而不是修改当前默认高周目基线。

### 12. 反编译源码 `Projectile::IsSplashDamage` 的火抗误差

`../PlantsVsZombies-decompilation/Lawn/Projectile.cpp` 中 `Projectile::IsSplashDamage()` 目前写成：只要 `mProjectileType` 非 0 且目标 `IsFireResistant()`，就返回非溅射。这个源码表达不等价于 PvZ 1.0.0.1051 原版二进制，后续审查 PE 时不要据此认为"西瓜/冰瓜命中冰车、投篮车、门板、梯子等火抗目标应取消溅射"。

原版 `PlantsVsZombies.exe` `Projectile::IsSplashDamage` 地址 `0x46d1f0` 的反汇编逻辑是：先检查 `mProjectileType == 0x6`，即 `PROJECTILE_FIREBALL`，只有火球/火豌豆才进入火抗短路；随后返回溅射类型集合 `0x3` 西瓜、`0x5` 冰瓜、`0x6` 火球。因此西瓜和冰瓜命中火抗目标仍应保持溅射，这也符合实战现象。

同一反编译文件里的 `Projectile::IsZombieHitBySplash()` 也只对 `mProjectileType == PROJECTILE_FIREBALL` 做 `IsFireResistant()` 排除，可作为项目内部旁证。PE 只对火球命中火抗目标取消溅射是正确方向；把瓜类也改成火抗取消溅射会引入新 bug。

### 13. 高地行 `mOnHighGround` 机制暂不覆盖

原版 `Zombie::CheckForHighGround()` / `Projectile::CantHitHighGround()` / `Plant::DoRowAreaDamage()` 中的 `mOnHighGround` 和 `GRIDSQUARE_HIGH_GROUND` 是高地行机制，不等同于屋顶/月夜的斜坡机制。PvZ 1.0.0.1051 正式版屋顶/月夜背景的行类型仍是普通行；屋顶斜坡通过 `StageHasRoof()` 下的 y 坐标偏移和 projectile 斜坡阻挡处理，而不是通过 `mOnHighGround`。

PVZ Wiki 归档 `技术/出怪机制` 也记录高地行在正式版已废除。PE 当前只支持常规六种场景类型，不支持废弃高地行；因此不要因为 `object/zombie.h` 缺少 `mOnHighGround`、`system/zombie/zombie_system.cpp` 缺少 `CheckForHighGround()` 或 `UpdateClimbingLadder()` 的高地高度分支，就默认列为屋顶/月夜待修 bug。

仍应关注的是屋顶斜坡本身会影响无尽测算的机制，例如直线 projectile 被斜坡阻挡、火豌豆撞斜坡时是否触发原版 `DoImpact(nullptr)` 溅射、屋顶炮飞行时间和落点等。这些属于屋顶斜坡机制，不应和废弃高地行机制混淆。

### 14. 阳光 coin 当前采用 direct-credit 经济抽象

PE 当前没有模拟原版 sun coin 对象生命周期。自然阳光在 `system/sun.cpp` 中倒计时归零后直接增加 `scene.sun.sun`，向日葵、阳光菇、双子向日葵等产阳植物也直接把产出折算为余额。这是当前无 UI、高初始阳光、无尽战斗测算场景下的 direct-credit 经济抽象，不等价于 PvZ 1.0.0.1051 原版 `Board::AddCoin()` -> coin 运动/收集前摇 -> `Coin::ScoreCoin()` -> `Board::AddSunMoney()` 的 native coin 语义。

因此，不要把“没有 sun coin 对象 / 没有收集前摇”默认列为必须立即修复的 PE bug；但也不要把 direct-credit 误认为原版经济行为。该差异会影响真实阳光经济、action 可用性、满阳光时产阳暂存、收集延迟、漏收风险，以及 rsvz 1051 后端与 PE 后端的严格帧级对齐。

短期用于 PvZWitness / rsvz parity 测试时，如果测试目标不是原版真实阳光经济，而是僵尸、植物、伤害、动画事件等战斗机制，应优先采用“经济归一化”测试模式：让 1051 harness / Witness / rsvz 测试后端把 sun coin 生成 hook 成 direct-credit，例如在 sun coin 生成点或 `Board::AddCoin` 的 sun coin 分支直接调用 `AddSunMoney(value)` 并跳过真实 coin 生命周期。此类测试结果只能说明 direct-credit 经济抽象下的后端一致性，不应用来验证 native sun coin 行为。

中期若 rsvz 或 Witness 需要同时支持 direct-credit 和原版经济，应新增显式能力 / 配置，例如 `SunEconomyPolicy::DirectCredit` 与 `SunEconomyPolicy::NativeLike`。PE 后端在未实现 native-like sun coin 生命周期前，遇到要求原版经济的测试或 API 应返回 unsupported 或明确拒绝，而不是伪造成功。真正的 native-like 实现需要建模 sun coin / pending sun、收集前摇、余额上限与满阳光暂存等语义，不能当作一两行的 trivial 修复处理。

### 15. `fire_cob` / 炮目标坐标 API 使用棋盘内目标约束

PE 的炮发射 API 面向无尽测算脚本中的逻辑目标点，不等价于原版 UI 鼠标点击路径。调用 `fire_cob`、`plant_cob_cannon::launch()` 或相关封装时，调用方应传入可点击棋盘内的有效目标坐标；越界坐标、左边界外坐标、过低 y 坐标等输入属于未支持 / 非目标输入，不要求复刻原版 `PixelToGridYKeepOnBoard()` 的 UI keep-on-board 行号夹取。

因此，不要把“越界炮目标行号没有按原版 UI 点击夹取”默认列为 PE 核心 bug。若上层项目需要接受任意像素点击语义，应在上层显式做输入校验、拒绝或归一化，或新增一个明确命名的 UI-compatible 炮目标 API；不要把当前逻辑炮 API 悄悄改成 UI hit-test 兼容语义。

### 16. 随机数只保证宏观统计，不保证同 seed 复现 1051

PE 保留 31-bit 基础随机输出、独立 Battle/Level 流和跨轮 Level seed `+101`。整数、浮点和加权抽样使用 1051 的一次取值、取模与累计边界，但自然允许类型仍采用直接合法候选抽样；PE 仍不保证整局同 seed 与 1051 生成相同对象、波表或逐次随机结果。

用于确定性跨后端测试时，可以显式启用每波出怪私有 Battle MT：在真实波次生成期间以 `base_seed + zero_based_wave` 建立私有流，但只在每次选行原子过程内启用。僵尸构造仍使用全局流；Locked 测试因此能获得各行不同的自然分布，同时不让1051未建模的声音、粒子或动画消耗改变后续僵尸。该能力不扩展到初始位置、速度、类型专属倒计时、整帧、后续战斗事件或 Level 流，也不改变默认关闭状态。若未来需要这些属性也具有可复现变化，应为具体玩法事实建立独立、按僵尸/用途派生的作用域，不得重新包住整个构造器。

不要为了对齐 Witness 的整局调用数量而补充 PE 未建模的 UI、视觉动画、阳光硬币横坐标等丢弃式随机调用，也不要让生产态随机入口始终维护调用摘要。PE 的普通随机正确性仍以平均炮伤、砸率、刷新、通关数量等宏观统计对照为准；局部私有流则用固定向量和跨后端 Witness 验证。

### 玩法对象与纯动画残留的边界

设计取舍：不保证对象池布局、回收顺序、死亡尸体显示字段或视觉/音频随机流与原版相同。
普通僵尸和巨人在逻辑死亡、完成死亡附带效果后直接删除，不另存尸体头部状态。
无头但 HP 尚未耗尽的僵尸继续自损、移动并阻挡子弹，不能按尸体删除（历史修复 #25）。
舞王及伴舞尸体仍保留必要死亡阶段：其引用存续影响补伴舞时机及舞群减速。
车辆已经进入的特殊死亡阶段继续按现有机制处理。

追踪刺只在目标永久缺失或逻辑死亡时删除；目标暂时不可攻击时继续保留。
植物近期受啃计时、攻击动画中参与伤害/动作判定的进度仍属于玩法状态。
RSVZ 的 Witness 排除纯尸体和池布局；常规自动操作需要的纯显示/音频接口可由 PE 空实现。
此项裁剪取代历史死亡动画完整保留的对齐目标，不是新增游戏机制 bug 修复。
